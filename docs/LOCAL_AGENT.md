# Orbit Local Agent v2

Локальный бизнес-агент с существующим интерфейсом Orbit. Чат выполняет настоящие вызовы инструментов: инспектирует SQLite, строит и исполняет SELECT, читает файлы рабочей папки. Графики и HR получают данные из локального бэкенда, а не из встроенной браузерной демо-базы.

## Запуск

Нужны **Node.js 20.3+** и **Python 3.10+** со стандартным модулем sqlite3. npm / pip-зависимостей нет. 

```bash
./start.command
```

Или на другом компьютере:

```bash
npm start
```

Откройте **http://localhost:3000**. Сервер слушает только `127.0.0.1`. Для другого порта: `PORT=4000 npm start`.

В репозиторий рабочая папка `workspace/` не включена. Сначала выполните `npm run init:sample`: скрипт создаст пример настоящей SQLite-базы и файлов. Данные вымышленные; база физически существует на диске и читается SQL-запросами. Если пример отсутствует: `npm run init:sample`. Скрипт инициализации не заменяет существующие файлы.

## Подключить базу компании

В UI: **Интеграции → Настроить подключение**:

1. Абсолютный путь к разрешённой рабочей папке.
2. Относительный путь SQLite (`company.sqlite`, `data/reporting.db`).
3. Источник: SQLite-таблица или локальный файл.
4. Таблица и соответствие полей (пустые значения определяются по схеме).
5. При необходимости — HR-файл, JSON диалогов и локальная Ollama-модель.

Изменения в UI действуют до перезапуска сервера. Постоянная конфигурация задаётся окружением:

```bash
ORBIT_WORKSPACE="/absolute/path/to/company" \
ORBIT_DB="data/company.sqlite" \
ORBIT_HR_FILE="hr/candidates.json" \
ORBIT_MESSAGES_FILE="communications/threads.json" \
npm start
```

Если Node не в PATH на этом Mac, с теми же переменными выполните `./start.command`. Python можно указать через `ORBIT_PYTHON=/absolute/path/to/python3`.

Реализован коннектор **SQLite**. PostgreSQL и MySQL в эту версию не входят. В SQLite можно использовать локальную reporting-копию данных компании.

## Финансовые поля

Обязательны `date`, `revenue`, `cost`. Дополнительно: `product`, `category`, `channel`. Поддерживаются некоторые синонимы (`дата`, `выручка`, `расходы`, `order_date`, `amount`, `expenses`). Для произвольной схемы задайте соответствие в настройках. Идентификаторы берутся только из проверенной схемы и экранируются.

- Дата — `YYYY-MM-DD`.
- Выручка и расходы — числа ≥ 0.
- Валюта интерфейса — KZT (₸).
- Прибыль = выручка − расходы; маржа = прибыль / выручка × 100.
- Последний месяц — последний доступный месяц в источнике.
- Рост — сравнение с предыдущим доступным месяцем.
- Суммы отражают только расходы в источнике, не являются автоматически полной бухгалтерской отчётностью.
- Если таблица больше 10 000 записей, частичный набор **не** выдаётся за полный финансовый отчёт. Создайте reporting-view с агрегацией или выберите меньший источник.

Произвольные SELECT доступны через **Аналитика → Схема и SQL** или прямо в чате. Для них выводятся таблица и явный признак ограничения результата.

## Файлы с диска

**Аналитика → Рабочая папка** показывает файлы, уже находящиеся в разрешённом workspace. Сервер читает их по относительному пути; браузерная загрузка не используется.

Поддерживаются **CSV, JSON, XLSX, TXT, MD**. Ограничения: файл до 5 МБ, табличный источник до 10 000 строк. В XLSX: первый лист либо лист по имени, до 200 колонок, распакованные данные до 30 МБ, строки/числа/булевы значения/даты. Формулы не исполняются: читается сохранённое Excel значение; при отсутствии кэша нужна пересохранённая книга. Старый бинарный `.xls`, `.xlsm`, PDF и DOCX в этой версии не поддерживаются.

Назначение файла можно выбрать в UI: финансовые записи, HR-резюме или диалоги. TXT/MD читаются и отображаются как текст; автоматический профессиональный скоринг требует структурированных полей кандидата.

HR: массив записей `name`, `experience`, `skills` (массив либо строка через запятую), необязательно `id`, `role`, `resume`. Либо таблица с полями `name`, `experience`, `skills`. Скоринг прежний: 70% навыки и до 30% за опыт до пяти лет; решение принимает человек.

Диалоги: JSON-массив `{id, name, channel, messages: [{from: "client" / "agent", text}]}`. Пример находится в `workspace/communications/threads.json`.

## Настоящий цикл инструментов

```text
Запрос в UI
 → POST /api/agent
 → get_db_schema()
 → генерация SQL по найденным таблицам и полям
 → execute_sql_query(query, params)
 → расчёт по результату
 → итоговый ответ + график
```

Для файлов используется `read_workspace_file(path, sheet?)`. Дополнительный инструмент `list_workspace_files()` даёт инвентарь папки. События передаются в UI через NDJSON по мере выполнения. В журнале видны инструмент, его аргументы (включая SQL), время и результат либо ошибка. Таймеров, изображающих вычисление, нет. Кнопка остановки прерывает HTTP-поток и выполняющийся дочерний процесс.

**Встроенный планировщик без LLM** поддерживает финансовые вопросы, явный месяц, «все периоды», схему БД, прямой SELECT, «Прочитай finance/sales.xlsx», HR, список файлов и контент-план. Он детерминирован, но выполняет настоящие инструменты и строит SQL по реальной схеме.

**Свободные задачи через локальную Ollama:** установите Ollama отдельно и локальную модель с поддержкой tool calling. Укажите точное имя установленной модели в интеграциях или `ORBIT_OLLAMA_MODEL`. Orbit обращается только к `http://127.0.0.1:11434/api/chat`, передаёт определения инструментов, выполняет вызовы, возвращает результаты модели и повторяет цикл до финального ответа. Максимум 8 итераций / 12 вызовов инструментов. Если модель не поддерживает инструменты, интерфейс покажет ошибку. Cloud-модели не поддерживаются. Модель в поставку не включена, автоматически ничего не скачивается.

API адаптера соответствует [официальной документации Ollama](https://docs.ollama.com/capabilities/tool-calling). Проверка Ollama-адаптера использует заглушку только для ответа модели, настоящие SQL-инструменты в тесте выполняются. Живая модель в окружении проверки не была установлена/запущена.

## Безопасность границы локальных инструментов

- SQLite `mode=ro`, `PRAGMA query_only`, отключённые расширения и authorizer с allowlist операций/функций.
- Один SELECT / WITH SELECT, параметризованные значения, максимум 10 000 строк / 5 МБ ответа.
- Прерывание SQL через 2 секунды и дочернего процесса через 6 секунд.
- Файлы только внутри текущего workspace: realpath-проверка, запрет абсолютных путей, `..`, скрытых файлов и выхода по symlink. Папка не раздаётся как статический ресурс.
- Только loopback; проверяются Host, Origin и Sec-Fetch-Site; CORS не включён.
- Конфигурация workspace управляется пользователем через локальный UI. Это доверенное локальное приложение, не сервер для публикации в интернет.
- Данные, история задач и черновики находятся в памяти браузерной сессии. После перезагрузки источники читаются заново; localStorage v1 не используется.
- Агент не меняет исходную БД и файлы. Черновики WhatsApp/Instagram не отправляются наружу; SMM-посты не публикуются. Шорт-лист и одобрение черновиков живут в текущей сессии.

Реализация SQLite основана на [URI read-only](https://www.sqlite.org/uri.html) и [SQLite authorizer](https://www.sqlite.org/c3ref/set_authorizer.html).

## API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | Версия и локальный режим |
| GET / POST | `/api/config` | Прочитать / изменить локальное подключение |
| GET | `/api/context` | Настоящие финансовые данные, кандидаты, диалоги |
| GET | `/api/workspace/files` | Файлы разрешённой папки |
| POST | `/api/tools/get_db_schema` | `{}` |
| POST | `/api/tools/execute_sql_query` | `{query, params?, limit?}` |
| POST | `/api/tools/read_workspace_file` | `{path, sheet?}` |
| POST | `/api/tools/list_workspace_files` | `{}` |
| POST | `/api/agent` | `{query, business?}`, JSON либо NDJSON через Accept |
| POST | `/api/analytics` | `{period?}`, читает настроенный источник |
| POST | `/api/hr/score` | `{}`, читает настроенный HR-источник |
| POST | `/api/reply` | `{threadId, business?}` либо `{text}` |
| POST | `/api/content-plan` | `{}`, строит план из локальной аналитики |

Переданные из браузера `rows` не заменяют локальные данные. Настройки подключения фиксируются на весь запуск задачи, чтобы параллельное изменение UI не меняло границы доступа уже идущего вызова.

## Проверка и структура

```bash
npm test
npm run check
```

`local/bridge.py` — файловая и SQLite-граница; `local/tools.mjs` — реестр инструментов и управление процессами; `local/context.mjs` — сопоставление схемы и доменные источники; `local/agent.mjs` — цикл планировщика / Ollama; `server.mjs` — локальный HTTP API; `dist/local-client.js` — транспорт и NDJSON; `dist/app.js` — сохранённый UI; `dist/engine.js` — чистые формулы и шаблоны. Демо-данные вынесены из клиентского движка в `scripts/sample-data.mjs` и используются только скриптом подготовки примера.

## Публичная ссылка

Публичное демо v1 и локальный агент v2 — разные способы запуска. Для доступа к диску и локальной БД нужно открыть интерфейс, обслуживаемый локальным сервером. Публичная страница не подключается к localhost и не получает доступ к вашим файлам. Эту версию нужно клонировать из GitHub и запускать на ПК получателя.

### Оформление

В верхней панели доступно переключение светлой и графитовой тёмной темы. Выбор сохраняется в браузере. Шрифт Comfortaa, движение по орбите и плавные переходы учитывают системную настройку уменьшения анимаций.
